# ADR-0009: Wild Rift ナレッジは自作する。LoL (PC) のデータを流用しない

- **Status**: Deferred
- **Date**: 2026-08-22
- **Deciders**: h.kawai

> 2026-10-07: 最初の対象タイトルを LoL (PC) に変えたため保留。Wild Rift の判断としては今も有効で、再開時にそのまま効く。詳細は [ADR-0012](0012-lol-pc-as-first-title.md)。本文は決定時のまま残す。

## Context

`knowledge` モジュールは Wild Rift のチャンピオン / アイテム / ルーン / パッチ情報を提供する。
用途は 2 つある:

1. 推論層（コーチング生成）が「このアイテムはこのパッチでどう変わったか」を参照する
2. 知覚層の言語化出力を制約する語彙（enum）を供給する
   （`docs/analysis/requirements/play-narration.md` FR-3）

既存の資産を流用できるなら自作したくない。2026-08 時点で調査した。

**事実:**

- **LoL (PC) 向けの MCP サーバーは複数存在する。** Riot API と Data Dragon をラップしたコミュニティ実装が
  多数公開されている（`mcp-riot`, `League-of-Legends-MCP`, `league-data-mcp`, `opgg-mcp`,
  `lol-client-mcp`, `riot-docs-mcp` 等）
- **Wild Rift 向けの MCP サーバーは見つからなかった。** 理由は構造的で、ADR-0002 のとおり
  **Riot に Wild Rift の公開 API が存在しない**（Developer API の対象は LoL(PC) / TFT / LoR / Valorant）。
  ラップする対象が無いため誰も作れていない
- **Wild Rift は LoL (PC) と別のバランス体系で運用されている。** アイテムプールが異なり、
  チャンピオンのスキルはリワーク / 簡略化されており、マップは鏡像、試合時間が短く、ルーンも別系統
- **パッチ番号の体系自体が独立している。** Wild Rift は 2026-08 時点で 7.2c 系であり、
  LoL (PC) の採番とは無関係
- Wild Rift のパッチ更新は概ね 2 週間サイクル
- 一次情報に相当する構造化データ源が存在しない。候補はいずれも二次情報:
  Riot 公式パッチノート（非構造テキスト）、Fandom の Wild Rift wiki、
  サードパーティ統計サイト（WildRiftFire / RiftGG / wr-meta / Rift Patch Notes 等）、
  個人開発の非公式 API（`statsWR`）

**推測:**

- 二次情報源のスクレイピングは各サイトの利用規約次第で可否が変わる。個別に確認が必要

## Decision

**Wild Rift ナレッジは自作する。LoL (PC) のデータ（Data Dragon / Riot API / 既存 MCP サーバー）を
Wild Rift のナレッジとして流用しない。**

流用は選択肢として明示的に却下する。理由:

> LoL (PC) のアイテムやスキルを前提に助言すると、**Wild Rift に存在しないアイテムを推奨する**。
> これは `docs/analysis/requirements/play-narration.md` で最上位の品質リスクに置いた
> 「もっともらしい嘘」を、こちらから作りに行く行為にあたる。コーチングプロダクトとして
> 最も避けるべき失敗そのもの。

付随する方針:

- ナレッジには **パッチバージョンを必ず持たせる。** 「いつ時点の情報か」が言えないデータは
  コーチングに使わない
- 語彙（チャンピオン名 / アイテム名 / ルーン名）は `knowledge` を単一の正とする。
  知覚層・推論層はここから enum を受け取る
- 鮮度維持（2 週間サイクルへの追従）を継続コストとして運用設計に織り込む
- CLAUDE.md のとおり、**ナレッジが引けなくてもコーチングは（精度を落として）成立させる。** 必須依存にしない

### この ADR で決めないこと

- **データ取得手段の選定** — 公式パッチノートのパース / wiki / サードパーティ / 手入力の
  どれをどう組み合わせるか。各サイトの利用規約確認を含めて別途詰める
- **`knowledge` の公開形式（MCP サーバー / ライブラリ / モジュール内直接呼び出し）と設置場所** —
  CLAUDE.md Open Decisions #2 のまま残す。

  なお MCP という形式の主な利点は、(a) 推論層の LLM にツールとして動的に引かせられること、
  (b) Claude Code から開発時に直接引けること、(c) 将来他プロダクトへ公開できること。
  一方で消費者が同一モノリス内の Kotlin モジュールであれば `@NamedInterface` 経由の直接呼び出しで足り、
  MCP は不便な RPC になる。**本質的な難所は転送形式ではなくデータ取得とスキーマ**であり、
  そこが解ければ MCP 化は薄い上物として後から被せられる。判断はデータモデル設計の後に行う

## Consequences

### 良くなること

- ナレッジの正しさを自分で保証できる。出典とパッチ時点が追跡可能になる
- Wild Rift 固有の語彙で一貫できる。知覚層の enum 制約（FR-3）が意味を持つ
- LoL (PC) との混同に起因する事実誤りを、データ層で構造的に排除できる

### 悪くなること / 引き受けるリスク

- **データ取得と鮮度維持が継続コストとして乗る。** 2 週間ごとのパッチ追従が必要
- 二次情報源に依存するため、上流の仕様変更・サイト構造変更・提供停止で壊れる。
  スクレイピングする場合は利用規約の確認が前提
- 網羅性が最初は不完全になる。MVP では対象範囲（主要チャンピオン / アイテムのみ等）を絞る判断が要る
- Phase 3（LoL (PC) 対応）では逆に Data Dragon / Riot API という一次情報が使える。
  ナレッジの抽象はタイトルごとに実装が分かれる前提で設計する（`GameTitle` の値オブジェクト）

### この決定を覆すときのコスト

「LoL (PC) データを流用する」方向に覆すことは想定しない（品質要求と矛盾する）。
一方で **Riot が将来 Wild Rift の公開 API を提供した場合**は、取得手段を差し替える価値がある。
そのため `knowledge` の内部を「データ取得」と「公開 API」に分け、取得側を差し替え可能にしておく。

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| LoL (PC) の Data Dragon / 既存 MCP サーバーを Wild Rift ナレッジとして流用する | **別ゲームのデータ。** アイテム・スキル・ルーン・パッチ体系がすべて異なり、存在しないアイテムを推奨する事故に直結する。最上位の品質リスクに真っ向から反する |
| LoL (PC) データをベースに Wild Rift 向けの差分を手で当てる | 差分が大きすぎて実質的に作り直し。かつ「どこが未修正か」が追えなくなり、誤りの発見が難しくなる。むしろ危険 |
| ナレッジ参照を諦め、LLM の内部知識だけでコーチングする | パッチ追従ができず、モデルの学習時点に固定される。アイテム名の捏造も止められない |
| `statsWR` 等の非公式 API に依存する | 個人運用のため可用性と継続性が保証されない。参考実装 / データ源の一候補としては見るが、依存先にはしない |
