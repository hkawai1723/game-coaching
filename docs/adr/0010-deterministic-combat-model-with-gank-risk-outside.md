# ADR-0010: 戦闘勝率は決定論的な数値計算で求め、ガンクリスクをモデル外に置く

- **Status**: Accepted
- **Date**: 2026-08-22
- **Deciders**: h.kawai

## Context

推論層（コーチング生成）が「その戦闘は仕掛けるべきではなかった」と言うには根拠が要る。
根拠を LLM の主観判断に置くと検証不能になり、`docs/analysis/requirements/play-narration.md` で
最上位の品質リスクに置いた「もっともらしい嘘」を推論層側で作ることになる。

ADR-0007 は知覚層について「数値・イベントは決定論的に取り、LLM には解釈だけをさせる」と決めた。
**同じ原則を推論層にも適用できるか**を検討した結果がこの ADR である。

**事実:**

- 戦闘のダメージ計算はゲーム内部で決定論的な数式として実装されている。
  **近似すべき未知関数ではなく、閉じた形が存在する既知の関数**である
- ADR-0002 のとおり Wild Rift には公開 API が無い。したがって
  **「完全な戦闘状態 + 結果」のラベル付きデータを機械的に収集する手段が存在しない**。
  動画から作るとしても知覚層が完成するまで 1 件も作れない
- 敵ジャングラーの位置は録画から観測できない。`play-narration.md` の観測可能性の境界で
  スコープ外に置いており、評価セットのグラウンドトゥルースにも書かない方針を採っている
- スキルショットの命中率は Phase 1 で実測する手段が無い

**推測:**

- 命中率が勝率計算における最大の誤差源になる

## Decision

### 1. 戦闘勝率は決定論的な数値計算で求める。機械学習を使わない

四則演算と条件分岐のみで構成する。確率的要素（命中・クリティカル等）はモンテカルロ
（同一の決定論的計算を乱数を振って反復する）で扱う。これは統計モデルでも学習でもない。

機械学習を却下する理由は 2 つあり、**どちらか一方だけでも決定的**:

- 正解の関数が厳密に既知である。既知の閉じた形を近似すれば精度が落ちるだけ
- 学習データが構造的に入手できない（公開 API が無い）

なお **Phase 2 の知覚層で CNN を使う方針（CLAUDE.md ロードマップ）とは無関係**である。
知覚層は「映像から数値を読む」ため関数が未知。戦闘計算は「数値が既にある前提」なので条件が逆になる。

### 2. `combat` モジュールを新設する

- 依存の向きは `combat → knowledge` の一方通行
- `coaching → combat` は port 経由
- 外部 I/O を持たない純粋ドメイン。Spring 非依存とし、ADR-0004 のドメイン層テスト方針に従う
- **プロダクト非依存に保つ。** Wild Rift 固有の語彙はデータ側（`knowledge`）に置き、
  エンジンはタイトルを知らない。判断基準は `payment` と同じ「別リポジトリにコピーしたら動くか」

### 3. モデル境界を「交戦そのもの」に引く。ガンクリスクは含めない

計算対象を 4 層に分け、**L2 と L3 の間に境界を引く**。

| 層 | 内容 | 性質 | 扱い |
|----|------|------|------|
| L0 ダメージ計算 | 防御貫通、軽減、レベル成長、スキル倍率、アイテム/ルーン効果 | 決定論 | `combat` |
| L1 交戦シーケンス | スキルローテーション、CD、マナ、キャストタイム、AA 間隔 → TTK | 決定論 | `combat` |
| L2 確率 | 命中、クリティカル、サモナースペル、ミニオン/タワーアグロ | モンテカルロ | `combat` |
| L3 文脈 | **ガンク**、ウェーブ状態、リスポーン、視界 | 観測不能を含む | **モデル外** |

境界をここに引く理由:

- **別の量である。** 「この交戦に勝てるか」はゲームの数式の性質で検証可能。
  「仕掛けるべきか」は隠れ情報下の意思決定で検証不可能。混ぜると、予測が外れたときに
  ダメージ計算が悪いのかガンク推定が悪いのか切り分けられない
- **ガンク確率は「観測できないと決めた値」の上に建つ。** 敵ジャングラーの位置を
  グラウンドトゥルースに書かないと決めておきながら、それを係数として計算に混ぜるのは、
  最上位の品質リスクを自ら作りに行く行為にあたる

### 4. ガンクは損益分岐点として出力する

ガンク確率 `g` を推定するのではなく、**期待値がゼロになる `g*` を解く**。

```
EV(fight) = (1 - g) · EV_1v1 + g · EV_ganked
g* : EV(fight) = 0 となる g
```

`g` は外部入力（あるいは未指定）とし、システムは `g*` だけを返す。
これにより観測不能な値を推定せずに済み、かつ「何を確認すべきだったか」を名指しできる。

> このデュエル自体は勝率 65%。損益分岐点は g\* = 22%。
> 直前 40 秒リバーの視界が無かったので、「敵ジャングラーが来ない確率が 78% 以上」と
> 言い切れる根拠が無ければこの仕掛けは期待値マイナス。

### 5. 出力は単一の勝率ではなく分布と分岐点にする

- P(勝ち) / P(相打ち) / P(負け) / P(離脱成功)
- **勝敗を分けた要因**（例: 「Q1 が当たった試行の勝率 88%、外した試行 21%」）
- **命中率の感度**（命中率を ±20% 振ったときの勝率の振れ幅）

「安定して勝つ 65%」と「スキル 1 発次第のコインフリップ 65%」は全く異なる助言になる。
点推定だけを返すとこの区別が消える。

命中率は Phase 1 で実測できない最大の誤差源なので、隠さず**明示的な調整パラメータ**として持ち、
感度を常に併記する。感度が大きい場合の正直な出力は「勝率 55%」ではなく「これはコインフリップ」である。

### 6. カバー範囲外は計算を拒否する

対応済みのチャンピオン / アイテムの範囲を明示し、範囲外が入力されたら
**近似値を返さず「非対応」を返す**。ADR-0009 と同じ原則。

これにより未対応分は「いつでも足せる作業」になり、「終わらせないとリリースできないもの」ではなくなる。

### この ADR で決めないこと

- **効果の合成モデル（加算 / 乗算 / 適用順）と、アイテム・スキル効果の表現方法** → ADR-0011
- **モデルの精度階層** — どこまでの誤差を許容するか。実測との突合後に決める
- **MVP のカバー範囲** — 対象チャンピオン / アイテムの具体的な選定

## Consequences

### 良くなること

- **検証可能な事実の土台ができる。** LLM 出力と違い、練習ツールで固定シナリオを録画して
  予測ダメージと実測を突合できる。ゴールデンテストとして CI に載る
- `knowledge` のデータ品質を機械的に測るテストハーネスになる。数値が誤っていれば実測と合わない
- 純粋関数の集合なので Spring 不要。`./gradlew unitTest` の数秒制約（ADR-0004）を壊さない
- コーチングの「なぜ悪手か」に数値の根拠が付く。LLM は説明の生成だけを担当すればよくなる
- `combat` は動画解析パイプラインに依存しないので**並行して進められる**。
  単体でもスタンドアロンのダメージ計算機として価値がある
- ガンクを分離したことで、Phase 3（LoL (PC) 対応）でも交戦計算はそのまま流用できる

### 悪くなること / 引き受けるリスク

- **命中率という検証不能なパラメータが残る。** 感度の併記で緩和するが消えない
- ガンクを扱わない以上、**単独では「仕掛けるべきだったか」に答えられない**。
  最終的な助言は推論層が `g*` と視界情報を突き合わせて組み立てる必要がある
- カバー範囲を絞るので、初期は「非対応」を返すケースが多くなる
- 実測との突合には練習ツールでの録画作業が要る。自動化できない手作業が発生する

### この決定を覆すときのコスト

- **ML への転向**は想定しない（学習データが構造的に得られない）。
  ただし将来 Riot が Wild Rift の公開 API を提供した場合は前提が変わりうる
- **ガンクをモデル内に取り込む**方向への転向は、`g` を外部入力として受け取る口を
  最初から開けてあるので安い。`g*` を返す実装はそのまま残せる
- 逆に**最初から混ぜてしまうと分離は高くつく**。だから今このタイミングで境界を決めている

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| 勝率を機械学習で予測する | 正解の関数が既知なのに近似する意味が無い。加えて学習データが構造的に入手不能（公開 API が無い）。さらにブラックボックスは「なぜ」を説明できず、コーチングの根拠として使えない |
| LLM に戦闘状況を渡して勝率を推定させる | 検証不能。数値の捏造を止められない。ADR-0007 で知覚層について却下したのと同じ理由 |
| ガンク確率を推定してモデルに組み込み、単一の勝率を返す | 観測不能な値（敵ジャングラー位置）の上に建つ。予測が外れたときの原因切り分けができない。評価セットの設計とも矛盾する |
| モンテカルロを使わず期待値のみ計算する | 分散が消える。「安定した勝ち」と「コインフリップ」が同じ数字になり、助言として質が落ちる。なお実装コストの差は for ループ 1 つ分しかない |
| 完全な戦闘シミュレータ（位置取り・カイティング・地形）を作る | ゲームエンジンの再実装になる。MVP では静的ステータスでの交戦に限定し、移動・追撃は扱わない |
| `coaching` モジュール内に計算ロジックを置く | コーチングのドメイン語彙と計算エンジンが混ざる。エンジンはタイトル非依存に保ちたい（Phase 3 で流用する）ので分離する |
