# ADR-0001: モジュラーモノリスを Spring Modulith で機械的に強制する

- **Status**: Accepted
- **Date**: 2026-08-19
- **Deciders**: h.kawai

## Context

api は Bounded Context が 7 つある（`api/web` / `match` / `analysis` / `coaching` / `knowledge` /
`user` / `payment`）。この規模で最初からマイクロサービスに割ると、運用コストが機能開発を上回る。
一方で 1 つの巨大なパッケージに全部入れると、境界が数週間で溶ける。

境界を「レビューで守る」運用は、AI 駆動で開発量が増えるほど破綻する。**人間のレビュー速度が
コード生成速度に追いつかない** ため、境界違反の検出は自動化しないと必ず漏れる。

## Decision

**単一デプロイのモジュラーモノリスにする。モジュール境界は Spring Modulith 2.0.5 で機械的に強制する。**

- モジュール間の直接呼び出しは禁止。公開 API（`@NamedInterface`）かドメインイベント経由のみ
- テーブルはモジュールが所有する。他モジュールのテーブルに FK を張らない。参照は ID のみ
- 循環依存禁止
- `ModularityTest` が `ApplicationModules.verify()` を実行する。**タグを付けないので `./gradlew unitTest`
  に含まれ、Spring コンテキストを起動せず 1 秒で回る**。境界違反はビルドで落ちる
- `Documenter` でモジュール図（PlantUML）を `build/spring-modulith-docs` に出力する

## Consequences

### 良くなること

- 境界違反が「レビューで指摘される問題」ではなく「ビルドが落ちる問題」になる
- 検証が速い（Spring 起動不要）ので、実装中の検証ループに入れられる
- 将来サービスとして切り出すときの切断面が、コードに明示されている状態を保てる

### 悪くなること / 引き受けるリスク

- モジュールを跨ぐ機能を書くとき、イベントか公開 API かの設計判断が毎回発生する。素朴な直接呼び出しより遅い
- Spring Modulith 2.0.x は比較的新しい。挙動が変わる可能性がある
- イベント経由の結果整合になる箇所が増える。トランザクション境界の設計が必要になる

### この決定を覆すときのコスト

- **モノリス → サービス分割** は安い。境界がすでに強制されているため、切り出す単位が既に決まっている
- **境界の強制をやめる** のは戻しにくい。一度緩めると依存が入り込み、再度締めるのは大工事になる

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| マイクロサービス | この規模では運用コストが機能開発を上回る。デプロイ・監視・分散トレースの整備が先に必要になる |
| 単純なレイヤードモノリス（境界は規約のみ） | 規約は破られる。AI 駆動で生成量が増えるほど、レビューでの検出が間に合わない |
| ArchUnit で境界ルールを手書き | ルールを自分で書く分だけメンテコストが乗る。Spring Modulith はパッケージ構造から規約で導出でき、モジュール図の出力も付いてくる |
