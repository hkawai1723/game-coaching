# ADR-0011: 戦闘効果の合成を段階パイプラインと宣言的モディファイアで表現する

- **Status**: Proposed
- **Date**: 2026-08-22
- **Deciders**: h.kawai

> 2026-10-07 注記（[ADR-0012](0012-lol-pc-as-first-title.md)）: 最初の対象は LoL (PC) になった。手順 A のデータ源は Riot 公式の Data Dragon が第一候補になる（本文の Fandom Wild Rift wiki / WildRiftFire は Wild Rift 用）。段階列の実測確認は LoL の練習ツールで行う。

## Context

ADR-0010 で `combat` を決定論的な数値計算モジュールとして作ると決めた。
残る問題は **アイテム効果とチャンピオン固有スキルをどう表現するか**である。

素朴な発想は「単純な計算 + 個別効果の足し合わせ」だが、これは 2 点で実態と合わない。

**事実:**

- **効果は加算とは限らない。** ダメージ増幅や被ダメージ軽減は乗算で合成される
  （軽減が乗算だからこそ複数重ねても 100% に到達しない）。防御による軽減は除算式
- **適用順序が結果を変える。** 貫通は「％ → 固定」の順で適用され、逆にすると値がずれる。
  順序の誤りは例外を出さず**静かに全数値をずらす**ので発見が遅れる
- Wild Rift のアイテム数・チャンピオン数は有限だが多い。素朴に個別実装すると
  効果 1 つにつきコード 1 箇所が増え続ける
- ADR-0009 のとおり Wild Rift の数値は自前で集める必要があり、
  **データのスキーマは `knowledge` と `combat` の両方に跨る**

**推測:**

- 効果の大半は「どの段階に、どの演算で、いくつ」の 3 つ組で表現できる。
  真に個別実装が要るのは少数のはず。**ただしこれは未検証の仮説である**

## Decision

### 1. 合成モデルを「段階パイプライン」にする

ダメージ計算を順序の決まった段階の列とし、**各段階が固有の合成規則を持つ**。

```
① 基礎ダメージ          加算
② 倍率寄与（AD/AP 係数） 加算
③ ダメージ増幅           乗算  (1+a)(1+b)…
④ 貫通                  順序依存（％ → 固定）
⑤ 防御による軽減         除算式
⑥ 被ダメージ軽減         乗算
⑦ シールド               減算・順序依存
```

**この段階列と各段階の合成規則は Wild Rift での実測により確定させる。上記は構造の骨格であり、
段の数・順序・式そのものが検証対象である。** ADR-0009 のとおり LoL (PC) の知識を流用しない。

段階が定義されていれば、個々の効果が加算か乗算かは個別判断ではなく
**「どの段階に入るか」から自動的に決まる**。ここが設計の急所で、
誤ると効果を追加していく途中で全面的な書き直しになる。

### 2. 効果はコードではなくデータとして宣言する

エンジンは段階と演算だけを実装する。効果は「どの段階に、どの演算で、いくつ、どの条件で」を宣言する。

```kotlin
data class Modifier(
    val stage: Stage,            // どの段階に入るか
    val op: Op,                  // ADD / MULTIPLY / OVERRIDE
    val value: Double,
    val condition: Condition? = null,
)
```

アイテム・ルーン定義は `knowledge` 側のデータとして持つ:

```yaml
- id: <item-id>
  stats: { ad: 55, crit_chance: 0.25 }
  modifiers:
    - { stage: crit_damage, op: multiply, value: 1.15 }
    - stage: damage_amp
      op: multiply
      value: 1.12
      condition: { target_hp_ratio_below: 0.4 }
```

**効果 N 個がコード N 箇所ではなくデータ N 行になる。** エンジン側は段階数 × 演算種を
実装した時点で増加が止まる。

### 3. 表現できない効果は個別実装を許容し、その数を管理指標にする

変身・独自スタック・対象指定の固有機構など、宣言では表せないものは個別コードを書く。
これは避けられない。重要なのは**個別実装の件数を可視化し、増えたら語彙の不足を疑うこと**。

### 4. 語彙は実物から帰納する。想像で設計しない

`Stage` と `Condition` の語彙は、机上で列挙せず**実在するアイテム / スキルから導出する**。

これを Accepted の条件とする（後述）。

### この ADR で決めないこと

- `Stage` / `Condition` の具体的な語彙 — 手順 A の結果で確定する
- データの物理フォーマット（YAML / JSON / DB）と `knowledge` での保持方法

## Accepted の条件（スパイク）

**この ADR は仮説「効果の大半は宣言で表現でき、個別実装は少数」に依存しているため Proposed とする。**
以下の調査で検証してから Accepted にする。

### 手順 A: 実物からの語彙帰納（見積もり半日）

1. 実際に使われているアイテム 25〜30 個と、チャンピオン 5 体のスキルを選ぶ
2. 効果を散文ですべて書き出す
3. それらを過不足なく表現できる**最小の `Stage` 集合と `Condition` 述語集合**を求める
4. 表現できないものに印を付ける ← 個別実装行き

### 判断分岐

| 結果 | 対応 |
|------|------|
| 個別実装行きが 1 割程度に収まる | **Accepted**。語彙を確定して実装に進む |
| 個別実装行きが半数近い | 段階の切り方が誤っている。段階列を再設計して手順 A をやり直す |
| そもそもデータ源に効果の正確な記述が無い | **ADR-0009 のデータ取得問題が先。** 本 ADR は保留 |

**手順 A の前に、データ源（Fandom Wild Rift wiki / WildRiftFire 等、ADR-0009 の候補）に
アイテムのパッシブ記述がどこまで正確に載っているかの確認が要る。** ここが埋まらないと
語彙の帰納そのものができない。

## Consequences

### 良くなること

- **「キリがない」問題が「有限のデータ入力作業」に変わる。** エンジンのコード量が
  効果の個数に対して増えなくなる
- 加算 / 乗算 / 順序の判断が段階の定義に一元化される。効果ごとに間違える余地が減る
- 効果の追加が `knowledge` のデータ更新だけで済む。パッチ追従（2 週間サイクル）の
  コストが下がり、コードのデプロイと切り離せる
- 宣言的なので、モディファイア単位のテストが書ける

### 悪くなること / 引き受けるリスク

- **段階列の設計を誤ると全面的な書き直しになる。** 効果を数十個入れた後に気づくのが最悪。
  だから手順 A を先に置いている
- `Condition` の語彙は放置すると DSL として肥大化する。述語の追加には歯止めが要る
- 宣言と個別実装の 2 系統が併存するため、どちらで書くべきかの判断が都度発生する
- 段階列の正しさ自体が Wild Rift での実測に依存する。実測なしには確定できない

### この決定を覆すときのコスト

段階列（`Stage` の定義と順序）を変えるコストが最も高く、既存のデータ行すべてに影響する。
逆に `Condition` の語彙追加や個別実装への逃がしは局所的で安い。
**リスクは段階列に集中しているので、そこだけを手順 A で先に潰す。**

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| 単純計算 + 効果を加算で足し合わせる | **実態と合わない。** 増幅・軽減は乗算、防御は除算式、貫通は順序依存。加算前提で作ると系統的に誤った数値を返し、しかも例外が出ないので気づかない |
| 効果ごとに個別のコードを書く（宣言モデルを持たない） | 効果の個数だけコードが増え続ける。パッチのたびにコード修正とデプロイが要る。加算 / 乗算の判断を効果ごとに繰り返すため誤りが入りやすい |
| 汎用のスクリプト言語（Lua 等）で効果を記述する | 表現力は十分だが、宣言でないため静的な検証ができず、テストもしにくい。5% の特殊ケースのために全体の検証可能性を捨てる取引になる |
| 効果を扱わず、基礎ステータスのみで概算する | アイテムのパッシブは戦闘結果を左右する。無視すると数値が実態から乖離し、ADR-0010 の「検証可能な事実の土台」という位置づけが成立しない |
