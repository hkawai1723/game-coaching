# ADR-0008: Phase 1 は LLM プロバイダーの API を直接叩き、マネージド基盤を採らない

- **Status**: Accepted
- **Date**: 2026-08-22
- **Deciders**: h.kawai

> 2026-10-07 注記（[ADR-0012](0012-lol-pc-as-first-title.md)）: Phase 1 は LoL (PC) を Riot API で扱うので、知覚層の Gemini は使わない。LLM は推論層だけになる。「直叩きにする」という決定は変わらないが、Context の「Bedrock に Gemini が無い」という論点は Phase 1 では効かなくなった。推論層のモデルが決まった時点（Open Decisions #1）で見直す条件に当たるか確認する。

## Context

ADR-0003 で知覚層に Gemini を使うと決めた。推論層のモデルは未定（CLAUDE.md Open Decisions #1）。
どちらも「プロバイダーの API を直接叩く」か「クラウドのマネージド基盤（AWS Bedrock / Google Vertex AI）
を経由する」かを決める必要がある。

**事実:**

- **Bedrock は Gemini を配信していない。** Bedrock のラインナップは Anthropic Claude / Amazon Nova /
  Meta Llama / Mistral / Cohere / AI21 / Stability など。Gemini を提供するマネージド基盤は Vertex AI (GCP) のみ
- したがって知覚層が Gemini である限り、**Bedrock に寄せても推論層しか一元化できない**。
  Bedrock を採ると AWS と GCP の両方を運用対象に抱えることになり、管理面はむしろ増える
- 実際の選択肢は 2 層 × 2 経路になる

  | 層 | 直叩き | マネージド |
  |----|--------|-----------|
  | 知覚層（Gemini） | Gemini API（API キー） | Vertex AI（GCP / IAM） |
  | 推論層（Claude を採る場合） | Anthropic API | Bedrock（AWS / IAM） |

- ADR-0003 の `PlayNarrator` port により、プロバイダー SDK の型はドメイン層に漏れない。
  呼び出し経路の変更は infrastructure 層に閉じる
- マネージド経路は IAM / サービスアカウント / ネットワーク設定の初期構築を要求する。
  直叩きは API キー 1 本で開始できる
- ストレージとモデル提供元が別クラウドの場合、動画・クリップの転送に egress 料金が発生する

**推測:**

- Phase 1 で必要になる機能（動画入力、構造化出力、キャッシュ）は直叩きで足りる。
  マネージド固有の機能（provisioned throughput 等）を要する要求は、現時点で立っていない

## Decision

**Phase 1 は Gemini API /（推論層に Claude を採る場合は）Anthropic API を直接叩く。
Bedrock も Vertex AI も採らない。**

実装方針:

- 呼び出しは **公式 SDK**（`google-genai` (Java) / `anthropic-java`）を使い、`PlayNarrator` などの
  port 実装の内側に閉じ込める
- **Spring AI のような汎用抽象レイヤーは挟まない。** port が既に抽象化の役割を負っており、
  二重の抽象になる。加えて Boot 4.1 / Kotlin 2.3 / JDK 25 という新しいスタックでの対応状況が未確認で、
  動画入力まわりの機能が抽象に乗り切らない懸念もある
- 生 HTTP による自前実装もしない。Gemini Files API の resumable upload 等、
  学習価値の低い定型処理に時間を使わない
- API キーは環境変数から読む。コードにもリポジトリにも置かない

### この決定を見直す条件

以下のいずれかが要求として立った時点で、マネージド経路への移行 ADR を書く:

- データレジデンシー要件、または動画を特定の VPC / クラウド外に出せないコンプライアンス要求
- 請求・調達の一元化が組織的に必要になる
- provisioned throughput によるレイテンシ保証が必要になる
- 顧客側が「特定クラウド内で完結していること」を要求する

## Consequences

### 良くなること

- スパイク（ADR-0007）を GCP / AWS の初期構築なしで始められる。検証ループの速さを優先する方針と整合する
- 従量課金と無料枠が実験フェーズに合う。1 解析あたりのコスト計測も素直にできる
- **API のセマンティクス（トークン会計、Files API のライフサイクル、構造化出力の制約のかけ方、
  レート制限とリトライのエラー意味論）を実際に扱うことになる。** これは port の粒度を決めるために
  必要な知識で、抽象の下で何が起きているか知らずに port を切ると抽象が漏れる

### 悪くなること / 引き受けるリスク

- プロバイダーごとに認証・レート制限・課金が分散する。キー管理とコスト集計を自前で設計する必要がある
- IAM による統合的な権限管理の恩恵を受けられない
- プロバイダー側の障害・レート制限・値上げをクラウド事業者のレイヤーで吸収できない
- **ストレージの置き場所と結合する。** S3 に動画を置いて Gemini に投げると egress が乗る。
  逆に Vertex AI + GCS なら GCS URI を直接参照でき egress も消える。つまり
  「知覚層をどこで動かすか」と「動画をどこに置くか」は独立に決められない。
  この依存関係を CLAUDE.md Open Decisions #4（DB・オブジェクトストレージ構成）の判断材料に含める。
  なお ADR-0007 のクリップ方式は転送量を大幅に減らすため、この論点の影響も小さくする

### この決定を覆すときのコスト

低い。`PlayNarrator` などの port 実装を差し替えるだけで、ドメイン層と他モジュールには影響しない。
Bedrock / Vertex AI はいずれも同じモデルを提供するため、プロンプトと評価セットはそのまま流用できる。
移行コストの主体は認証・ネットワーク設定であって、アプリケーションコードではない。

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| Bedrock に一元化する | **Bedrock に Gemini が無い**ため前提が成立しない。知覚層は別経路になり、AWS + GCP の二重運用になる。一元化の利点が出ない |
| Vertex AI に一元化する | 知覚層は成立するが、推論層に Claude を採る場合（Open Decisions #1）は別経路が必要。かつスパイク段階で GCP の初期構築コストを払う動機が無い。egress の観点では有利なので、ストレージ構成を決める時点で再評価する |
| Spring AI で抽象化して両対応にする | port が既に抽象化の役割を担う。二重の抽象は保守対象を増やすだけ。新しいスタックでの対応状況も未確認 |
| 生 HTTP で自前実装する | 学習量は最大だが、resumable upload 等の定型処理に時間を溶かす。得られる知識が投資に見合わない |
