# ADR-0004: テストを 3 層に分け、ドメイン層は Spring を使わない

- **Status**: Accepted
- **Date**: 2026-08-19
- **Deciders**: h.kawai

## Context

AI 駆動で開発する。この前提だと **検証ループ 1 回の所要時間が、そのまま生産性の上限になる。**
「実装 → テスト → 結果を見て直す」を 1 日に何十回も回すため、1 回 60 秒のループと 3 秒のループでは
到達できる品質が変わる。

素朴に `@SpringBootTest` でテストを書くと、コンテキスト起動だけで数十秒かかる。
さらに LLM を実際に叩くテストが混ざると、**ゲートを回すたびに課金が発生する。**

## Decision

**テストを 3 層に分ける。**

| 層 | 書き方 | タグ | 実行コマンド |
|----|--------|------|-------------|
| ドメイン / アプリケーション | **純粋な Kotlin。`@SpringBootTest` 禁止** | なし | `./gradlew unitTest`（秒） |
| モジュール統合 | `@ApplicationModuleTest` / `@SpringBootTest` | `@Tag("integration")` | `./gradlew test` |
| 外部 API 実呼び出し | LLM 等を実際に叩く | `@Tag("external")` | 常に除外。明示指定時のみ |

- `@Tag("external")` は `build.gradle.kts` で **すべての Test タスクから常に除外する。**
  ゲートで課金を発生させない
- **時刻・ID 生成・乱数は port 化して注入する。** これでドメインテストが決定論的になり、
  Spring も DB も要らなくなる
- モジュール境界検証（`ApplicationModules.verify()`）はタグを付けない。**`unitTest` に含める**
  （Spring 起動不要なので速い）

## Consequences

### 良くなること

- 実装中の検証ループが数秒で回る
- 境界違反が最速のゲートで落ちる
- 外部 API のコストとレート制限が、日常のビルドに影響しない

### 悪くなること / 引き受けるリスク

- **`unitTest` が緑でも配線は保証されない。** Bean 定義や設定ミスは `./gradlew build`（= `test` を含む）
  まで落ちない。緑の意味を取り違えない
- port 化のために抽象が増える。`Clock` / `IdGenerator` のような小さい interface が並ぶ
- `@Tag("external")` のテストは日常的に回らないので腐る。**リリース前に明示的に回す運用が要る**

### この決定を覆すときのコスト

安い。タグを外して 1 つの `test` タスクに戻せばよい。ただし戻すと検証ループが遅くなり、
その遅さは全開発期間にわたって効き続ける。

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| すべて `@SpringBootTest` で書く | 検証ループが遅くなり、AI 駆動開発の生産性が落ちる。この 1 点で却下 |
| 外部 API テストをモックだけで済ませる | プロバイダーの実挙動（レート制限、出力形式の揺れ）を一度も踏まないままリリースすることになる。分離して残す |
| タグではなく sourceSet を分ける | Gradle 設定が重くなる割に得るものが同じ。タグで足りる |
