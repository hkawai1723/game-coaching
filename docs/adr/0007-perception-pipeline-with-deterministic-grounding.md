# ADR-0007: 知覚層を決定論的抽出で接地した多段パイプラインにする

- **Status**: Proposed
- **Date**: 2026-08-19
- **Deciders**: h.kawai

## Context

ADR-0003 で知覚層（動画 → 行動ログ）を Gemini の動画理解で実装すると決めた。
当初想定していた実装方式は「mp4 全編を 1 回の呼び出しで JSON 化する」**全編一括方式**。
これに対して精度上の懸念がある。事実と推測を分けて書く。

**事実:**

- Gemini の動画理解は既定で低頻度（~1fps）のフレームサンプリング。Wild Rift の集団戦は
  数秒で決着するため、因果（スキルの撃ち合い、フォーカス、位置取り）がフレーム間に落ちうる
- 長尺動画は入力トークンが大きい。解像度・トークンを抑えると、HUD の小さい表示
  （ゴールド / CS / タイマー / ミニマップ）の読み取りが不安定になる
- LLM の出力は非決定的で、読み取れない値を補完（捏造）することがある。コーチングに
  事実誤りが 1 つ混ざるだけでユーザーの信頼を失う（要求整理 `docs/analysis/requirements/play-narration.md`）
- 一方、HUD とリザルト画面（最終スコアボード）はレイアウト固定であり、
  LLM を使わず決定論的（OCR）に抽出できる

**推測（スパイクで検証する）:**

- 全編一括方式では、キーモーメントの因果と数値の精度がコーチングに耐えない
- 短いクリップ + 焦点を絞ったプロンプトの方が言語化の精度が大きく上がる

## Decision

知覚層を、単一の LLM 呼び出しではなく **3 段のパイプライン** として設計する。

```
mp4
 ├─ ① 決定論的抽出（LLM 不使用）
 │     ・リザルト画面のスコアボード → 確定 ground truth
 │     ・N 秒ごとの HUD クロップ → ゴールド / KDA / タイマーの時系列骨格
 ├─ ② イベント検出（機械的）
 │     ・骨格タイムラインからデス / キル / オブジェクト / ゴールド急変点を特定
 └─ ③ 言語化（ここで初めて Gemini の動画理解）
       ・キーモーメント前後 ±20〜30 秒のクリップを高解像度で投入
       ・「このデスに至る 30 秒で何が起きたか」という焦点の絞られたプロンプト
       ・strict schema + エンティティ名は knowledge 由来の enum に制約
       ・①と突合し、矛盾する narration は棄却 / 再試行
```

原則:

- **数値・イベントの「事実」は決定論的抽出が正。LLM には「解釈」だけをさせる**
- 中間成果物（フレーム、OCR 結果、クリップ、narration、突合結果)をすべて保存する
- 3 段全体を `PlayNarrator` port の裏に閉じる。他モジュールからパイプライン構造は見えない

### 検証方針（Accepted にする条件）

実装に入る前にスパイクを 1 本行う:

1. 実際の Wild Rift 動画 1〜2 本に人手で正解イベントログを付ける（評価セットの第 1 号を兼ねる）
2. (a) 全編一括方式 と (b) 本 ADR のクリップ方式 の両方で行動ログを生成し、正解と突合する
3. HUD OCR の安定性（端末解像度・録画品質・HUD スケールのばらつき）を確認する

判断基準:

- (b) が (a) を精度で明確に上回る → 本 ADR を **Accepted** にして実装に入る
- (a) で十分な精度が出る → パイプラインを簡略化する ADR を新規に書き、本 ADR を **Superseded** にする
- OCR が不安定 → 段①の実装手段を再検討する（クロップ画像を安価な画像モデルに投げる等。
  パイプライン構造自体は維持）

## Consequences

### 良くなること

- 数値の捏造をアーキテクチャで抑止できる（事実は OCR、解釈は LLM という役割分担）
- LLM への動画入力が全編 → 数分ぶんのクリップに減り、1 解析あたりのコストが下がる。
  「LLM コストが支配的」という制約に直接効く
- 「あなたの N 回のデス、それぞれ何が起きたか」というコーチングとして自然な構造が
  言語化の段階で手に入る。タイムスタンプ付きなのでフロントの動画シークと連動できる
- 段①②は Phase 2 で内製する知覚層（CNN + OCR + 状態機械）の置き換え対象そのもの。
  差し替え境界が最初から明確になり、中間成果物がそのまま学習・評価データとして貯まる

### 悪くなること / 引き受けるリスク

- 全編一括より実装が複雑。段ごとの失敗モードとリトライ・部分的成功の設計が必要
- OCR は録画品質・言語設定・HUD スケール差に脆い可能性がある（スパイクで確認）
- Wild Rift クライアントの更新で HUD レイアウトが変わると段①が壊れる。
  レイアウト定義（クロップ座標等）をコードから分離し、追従コストを下げる
- クリップ切り出し等の動画処理（ffmpeg 等）が実行環境の依存に加わる

### この決定を覆すときのコスト

パイプライン全体を `PlayNarrator` port の裏に閉じるため、覆しても他モジュールに影響しない。
段の削除・差し替え・簡略化は port 実装内で完結する。スパイクの評価セットは方式に依存しない
資産として残る。

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| 全編一括で Gemini に投げる（当初想定） | 上記の精度懸念。ただし推測を含むため、スパイクで実測比較し、十分ならこちらに戻す（Superseded の逃げ道を残す） |
| 最初から CNN + OCR で知覚層を完全内製 | ADR-0003 で却下済み。評価基準が無いまま数か月を消費する |
| 高解像度・高頻度サンプリングで全編を投げて精度を金で解決 | 1 解析あたりの LLM コストが支配的という制約に真っ向から反する。課金モデルが成立しない |
| リザルト画面のスクリーンショットを別途アップロードさせる | 入力が 2 つになり UX が悪い。録画にリザルトまで含める誘導（FR-6）で足りる |
