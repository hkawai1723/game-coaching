# ADR-0005: payment をプロダクト非依存の再利用モジュールとして扱う

- **Status**: Accepted
- **Date**: 2026-08-19
- **Deciders**: h.kawai

## Context

決済とサブスクリプション管理は、このプロダクト（ai-game-review）と `../upagu` の両方で必要になる。
実装を 2 か所に持つと、Stripe の Webhook 処理・冪等性・失敗時のリカバリという
**間違えると金銭事故になる部分が二重管理** になる。

一方で、共通化を焦って最初からライブラリに切り出すと、まだ形が定まっていない段階で
インターフェースを固定することになる。

## Decision

**`payment` は api の中の 1 モジュールとして実装する。ただし、いつでも切り出せる状態を保つ。**

- **Wild Rift / コーチングのドメイン語彙を `payment` の中に持ち込まない。**
  `Match` / `PlayNarrator` / `Coaching` といった語が `payment` パッケージに現れたら設計ミス
- **依存の向きは他モジュール → `payment` の一方通行。逆はイベント購読も含めて禁止**
- 判断基準は **「このモジュールを別リポジトリにコピーしたら動くか」**。答えが No なら直す
- `payment` に変更を入れるときは upagu 側への影響を確認する

**ライブラリまたは独立サービスとして実際に切り出すのは、この ADR では決めない。**
両プロダクトで要件が固まってから判断する。

## Consequences

### 良くなること

- モジュラーモノリスの中にいるので、切り出す前の段階では開発が速い（デプロイもリポジトリも 1 つ）
- 「コピーして動くか」という具体的な基準があるので、境界の判断がレビューでブレない
- Spring Modulith が依存の向きを機械的にチェックする（ADR-0001）ので、逆向き依存はビルドで落ちる

### 悪くなること / 引き受けるリスク

- **2 リポジトリ間で実装がドリフトする。** 現時点では手作業で揃えるしかない
- プロダクト固有の課金要件（「解析 1 回あたり」のような従量課金）を `payment` に入れたくなる圧力が常にかかる。
  ここを守り続けるのはレビューの仕事になる
- 抽象を保つために、プロダクト側に薄い変換層が必要になる

### この決定を覆すときのコスト

- **切り出す方向**は安い。制約を守っている限り、コピーして動く状態を維持しているため
- **プロダクト固有にする方向**（再利用をやめる）は、upagu 側に実装を複製する必要があり高い

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| 最初から独立サービスにする | 両プロダクトで要件が固まっていない。今インターフェースを固定するのは早い |
| 最初から共有ライブラリに切り出す | 上と同じ。加えてバージョニングと公開の手間が、得られる再利用性に見合わない |
| プロダクトごとに独自実装する | Stripe Webhook の冪等性・失敗リカバリという事故りやすい部分を二重に持つことになる |
