# ADR-0013: MVP のコーチング生成には Gemini を使い、差し替えられる形にしておく

- **Status**: Accepted
- **Date**: 2026-10-12
- **Deciders**: h.kawai

## Context

CLAUDE.md Open Decisions #1（フィードバック生成のモデルを Claude と Gemini のどちらにするか）が
決まっていないと、コーチング生成のストーリー（COACH-13）に着手できない。
プロンプト設計は「未決定を前提にしない」方針なので、MVP 用に先に決める。

**事実:**

- Phase 1 で LLM を使うのはコーチング生成だけ（ADR-0012）。入力は timeline の全量ではなく、
  決定論的に組み立てた行動ログ（COACH-10）
- ADR-0008 で、プロバイダーの API を公式 SDK で直接叩き、port の裏に閉じ込めると決めている。
  コーチング生成の port は `CoachingAdvisor`（`coaching` モジュール）
- MVP では録画の解析も扱う（COACH-17 で ADR-0012 を部分的に見直す予定）。
  動画を入力にできるマネージドでない API は Gemini にある（ADR-0003 の調査）
- 2026-10 時点の Gemini API の Flash 系 GA モデルは `gemini-3.6-flash` とされている
  （公式ドキュメントで確認してから設定値に入れる）

**推測（未確認）:**

- 行動ログ 1 試合分は数千〜1 万トークン程度に収まる見込み。Flash 系なら 1 試合のコストは
  1 円前後になる（COACH-13 で実測する）
- 日本語のコーチング文の品質に、MVP の用途で問題になるほどの差は Claude と Gemini の間で無い
  （評価セットが無いので比べられていない）

## Decision

**MVP のコーチング生成は Gemini API（Flash 系）を使う。ただし、後で Claude などに替える前提で作る。**

- 公式の Java SDK（`google-genai`）を `CoachingAdvisor` の実装（例: `GeminiCoachingAdvisor`）の中だけで使う。
  Gemini の型を `coaching` のドメイン層に出さない
- モデル ID は設定（環境変数）で渡す。コードに書かない。API キーは `GEMINI_API_KEY`
- 出力は構造化出力（JSON スキーマ指定）で受け取る。スキーマは **ドメイン側で定義** し、
  プロバイダーの機能はそれを強制する手段として使う。プロバイダー固有のスキーマ表現に設計を合わせない
- プロンプトはバージョン付きのリソースファイルにする。生成結果には
  プロバイダー・モデル ID・プロンプトのバージョンを保存する（どれで生成したか後から比べられるように）
- キャッシュキー（content hash）にプロバイダーとモデル ID を含める

### 差し替えを判断する時点

次のどちらかで、Claude との比較をやり直す。結果は新しい ADR に残す:

- COACH-16（Sprint 4 の振り返り）でコーチング品質を rubric で採点したとき
- 評価セット（人手で正解を付けた試合）が揃い、同じ行動ログで両モデルを比べられるようになったとき

## Consequences

### 良くなること

- COACH-13 に着手できる
- 動画理解（COACH-17 以降）も Gemini にするなら、キー・SDK・課金が 1 本で済む
  （COACH-17 で別のモデルにしてもよい。この ADR は動画のモデルを決めない）
- Flash 系は安いので、プロンプトの試行錯誤を気にせず回せる

### 悪くなること / 引き受けるリスク

- 評価セット無しで決めているので、品質の根拠は無い。差し替えの前提はそのため
- 差し替えたとき、プロンプトはそのままでは移らない。
  プロンプトのバージョンと生成結果をセットで保存しておくことで、比較はできるようにしておく
- 構造化出力の制約（使えるスキーマの機能）はプロバイダーごとに違う。
  ドメインのスキーマを、どちらでも表せる範囲（オブジェクト・配列・文字列・数値・enum）に抑える

### この決定を覆すときのコスト

低い。`CoachingAdvisor` の実装を 1 つ足し、設定で切り替えるだけ。ドメイン層と他モジュールは変わらない。
コストの大半は、新しいモデル向けのプロンプト調整と、評価セットでの比較。

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| Claude（Anthropic API）にする | 品質で劣るという根拠は無い。動画理解も視野に入れると、MVP はキーと SDK を 1 本にまとめたい。評価セットができたら比べ直す |
| 両方実装して切り替えられるようにしておく | 2 本目の実装は、比べる材料（評価セット）ができてからで間に合う。今は YAGNI |
| Pro 系の上位モデルにする | 行動ログを読んで指摘を絞る程度のタスクで、まず安いモデルで品質を見る。足りなければ設定でモデル ID を替える |
