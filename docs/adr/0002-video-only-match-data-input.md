# ADR-0002: 試合データの入力経路を動画のみとする

- **Status**: Superseded by ADR-0012
- **Date**: 2026-08-19
- **Deciders**: h.kawai

> 2026-10-07: 最初の対象タイトルを LoL (PC) に変えたため、入力経路を Riot API に置き換えた。詳細は [ADR-0012](0012-lol-pc-as-first-title.md)。本文は決定時のまま残す。

## Context

対象は Wild Rift（モバイル版 LoL）。コーチングには試合中に何が起きたかのデータが要る。

**Riot の Developer API に Wild Rift は含まれていない**（対応タイトルは LoL(PC) / TFT / LoR / Valorant）。
つまり LoL(PC) 向けのコーチングツールが当たり前に使っている `match-v5` 相当の構造化データが、
このプロダクトでは一切取得できない。ここが LoL(PC) 向けプロダクトとの決定的な違いになる。

入力経路の候補は実質「プレイヤーがアップロードする試合動画」しかない。

## Decision

**Phase 1 の試合データ入力経路は、プレイヤーがアップロードする動画のみとする。**

- 動画以外の入力（手入力、スクリーンショット、リプレイファイル）は実装しない
- 入力経路は `MatchSource` port の裏に置く。現時点の実装は `VideoMatchSource` の 1 つだけ
- 対応タイトルは値オブジェクト `GameTitle`（`WILD_RIFT` / `LOL`）で表現する。boolean フラグにしない
- **LoL(PC) 用の実装（`RiotApiMatchSource`）は書かない。** 拡張の余地を型で残すだけに留める（YAGNI）

## Consequences

### 良くなること

- 入力が 1 経路に絞られるので、Phase 1 のスコープが小さく保てる
- port を切っておくことで、Phase 3 の LoL(PC) 対応で既存モジュールを書き換えずに済む

### 悪くなること / 引き受けるリスク

- **データ品質が動画の品質に依存する。** 解像度・フレームレート・UI 言語・端末の差がそのまま解析精度に効く
- 動画のストレージコストと転送コストが常時かかる
- **1 試合あたりの解析コストがマルチモーダル LLM の料金に直結する。** 課金モデルの設計が必須になる
  （CLAUDE.md の Open Decisions #6）
- 「試合をプレイしたらすぐ自動で解析」ができない。プレイヤーが録画してアップロードする手間が残る

### この決定を覆すときのコスト

Riot が Wild Rift の API を公開したら覆せる。`MatchSource` port の実装を足すだけで、
`match` より下流のモジュール（`analysis` / `coaching`）は影響を受けない設計にしてある。

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| Riot Developer API を使う | **Wild Rift は対応していない。** 選択肢として成立しない |
| プレイヤーが試合結果を手入力する | 入力負荷が高く、そもそもコーチングに必要な時系列の情報が取れない |
| 端末上でリアルタイムにキャプチャするクライアントを配る | モバイル端末での常駐キャプチャは実装・審査・電池消費のいずれもコストが高い。Phase 1 の検証には過剰 |
