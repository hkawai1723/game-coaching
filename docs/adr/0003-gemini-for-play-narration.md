# ADR-0003: 動画 → プレイ行動の言語化に Gemini を使う

- **Status**: Accepted
- **Date**: 2026-08-19
- **Deciders**: h.kawai

## Context

パイプラインは 2 段ある。

```
動画 → [知覚層] プレイ行動の言語化 → 行動ログ → [推論層] コーチング生成 → フィードバック
```

知覚層は「動画から何が起きたかを構造化する」処理。ADR-0002 のとおり入力は動画しかないので、
ここが成立しないとプロダクト全体が成立しない。

Phase 1 の目的は **「使えるコーチング」の基準を作ること** であって、解析基盤を内製することではない。
自前の知覚モデル（CNN + OCR + 状態機械）を先に作ると、評価基準が無いまま数か月を消費する。

## Decision

**Phase 1 の知覚層は Gemini のマルチモーダル（動画理解）で実装する。**

- `analysis` モジュールに `PlayNarrator` port を置き、実装を `analysis/infrastructure/gemini/GeminiPlayNarrator` に置く
- **Gemini の型（SDK のリクエスト/レスポンス）をドメイン層に漏らさない。** port の入出力は自前のドメイン型
- 出力は構造化された行動ログ。自由文の要約にしない（推論層が機械的に扱えなくなるため）
- 呼び出しは **非同期・冪等・キャッシュ可能** にする。同じ動画を二度解析して二度課金しない
- 実際に Gemini を叩くテストには `@Tag("external")` を付け、通常のビルドから常に除外する（ADR-0004）

**推論層（コーチング生成）を Claude と Gemini のどちらに投げるかは、この ADR では決めない。**
CLAUDE.md の Open Decisions #1 のまま残す。決まったら別の ADR を書く。

## Consequences

### 良くなること

- 知覚層を数日で立ち上げられる。Phase 1 の目的（コーチング品質の基準づくり）に時間を使える
- モデル側の改善がそのまま精度改善になる

### 悪くなること / 引き受けるリスク

- **1 試合あたりのコストが支配的になる。** 動画は入力トークンが大きい。課金モデルの設計が必須
- レイテンシが大きい。同期 API で返せないので、解析ジョブの状態管理（`match` モジュール）が必要
- 出力が非決定的。**同じ動画から毎回同じ行動ログが出るとは限らない**。評価セットが無いと退行に気付けない
- プロバイダー側のモデル終了・値上げ・レート制限をこちらで制御できない

### この決定を覆すときのコスト

`PlayNarrator` port の実装を差し替えるだけで済むように設計する。**この port が Phase 2（自社 AI）の
差し替え境界そのもの。** 知覚層は HUD・ミニマップ・KDA・ゴールド・タイマーという決定論的で
レイアウトが固定な対象を扱うので、CNN + OCR + フレーム間ヒューリスティクスで置き換えられる余地が大きい。

そのために **Phase 1 の時点から、動画・行動ログ・フィードバック・ユーザーの反応を、後から学習と評価に
使える形で保存する**（利用規約・同意の設計も込みで）。これをやらないと Phase 2 の入口に立てない。

## Alternatives Considered

| 案 | 却下理由 |
|----|---------|
| 最初から自前の CNN + OCR で知覚層を作る | 「良いコーチングとは何か」の基準が無いまま作ることになる。評価セットが先。Phase 2 でやる |
| フレームを静止画に落として画像モデルに投げる | 時系列（誰がいつどこに動いたか）が落ちる。コーチングに必要な情報の大半が失われる |
| Claude のマルチモーダルで知覚層をやる | 現時点で長尺動画の直接入力に対する適合が Gemini ほど明確でない。推論層での採用は Open Decisions #1 として別途検討する |
