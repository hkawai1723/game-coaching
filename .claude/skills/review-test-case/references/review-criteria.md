# テストケースレビュー基準

ブラックボックス E2E テスト仕様書のレビュー観点。
各観点について PASS / WARN / FAIL で判定する。

## 1. 網羅性

- [ ] 変更されたすべての画面・機能がテストケースでカバーされている
- [ ] 新規追加された API エンドポイントに対応するテストケースがある
- [ ] 変更された既存機能の回帰テストが含まれている
- [ ] 設計ドキュメント（ユースケース・画面遷移）の主要フローがカバーされている

## 2. カテゴリバランス

- [ ] 正常系テストケースが存在する
- [ ] 異常系テストケースが存在する（エラー入力、エラーメッセージ確認）
- [ ] 境界値テストケースが存在する（空入力、最大文字数、上限・下限）
- [ ] 正常系だけに偏っていない（異常系 + 境界値が全体の 30% 以上）

## 3. テストケースの独立性

- [ ] 各テストケースが他のテストケースに依存せず単独で実行可能
- [ ] 前提条件にデータの事前準備が必要な場合、その手順が明記されている
- [ ] テストケースの実行順序に依存しない

## 4. 前提条件の明確さ

- [ ] テスターが再現可能な具体的条件が記載されている
- [ ] 「なし」ではなく実際に前提条件がない場合のみ「なし」が使われている
- [ ] ログイン状態、データの有無、設定状態など必要な条件が漏れなく記載されている

## 5. 期待結果の検証可能性

- [ ] テスターが画面上で目視確認できる具体的な条件になっている
- [ ] 「正しく動作する」「適切に表示される」等の曖昧な表現がない
- [ ] 画面遷移先、表示されるメッセージ、データの状態変化が具体的に記載されている
- [ ] エラーケースではエラーメッセージの内容まで記載されている

## 6. 優先度の妥当性

- [ ] High: コア機能・クリティカルパスに適切に設定されている
- [ ] Low: エッジケース・軽微な動作確認に適切に設定されている
- [ ] High が全体の 50% 以下（すべてが High なら優先度の意味がない）
- [ ] リスクの高い変更（決済、認証等）は High に設定されている

## 7. 重複の排除

- [ ] 同一の操作・期待結果を検証するテストケースが重複していない
- [ ] 類似テストケースが統合可能な場合、統合されている
- [ ] カテゴリ違い（正常系 vs 異常系）で同じ画面を重複テストする場合は許容

## 8. セキュリティ観点

- [ ] 認証が必要な機能に対して未認証アクセスのテストがある
- [ ] 権限制御がある機能に対して権限不足のテストがある
- [ ] 入力フィールドに対するインジェクション系のテストがある（該当する場合）
- [ ] セッション・トークン関連の変更がある場合、有効期限切れのテストがある

## 9. 画面名・用語の一貫性

- [ ] 画面名が設計ドキュメント（screen-transition.md 等）と一致している
- [ ] 同じ画面が異なる名称で記載されていない
- [ ] ボタン名・ラベル名の表記が統一されている

## 10. フォーマット準拠

- [ ] テストケース ID が `TC-XXX` の連番になっている
- [ ] 全フィールド（カテゴリ、優先度、画面、前提条件、操作概要、期待結果、テスト手順、備考）が記載されている
- [ ] テスト手順が `--`（未記入マーカー）になっている（この段階では記入しない）
- [ ] メタ情報（対象機能、ブランチ、作成日等）が記載されている

## 判定基準

| 判定 | 条件 |
|------|------|
| PASS | すべての観点で問題なし |
| WARN | 軽微な改善点あり（レビュアーが修正して続行） |
| FAIL | 重大な欠陥あり（テストケースの追加・修正が必要） |

### FAIL になるケース

- 変更された機能のテストケースが完全に欠落している
- 正常系テストケースが 1 件もない
- 期待結果が曖昧で検証不可能
- テストケース ID が重複している
